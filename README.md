# stock-insight

DART 실적 공시를 숫자로 정리하고, LLM이 그 숫자만 가지고 짧게 요약해 주는 공시 분석 서비스입니다.

## 만든 이유

주식을 하면서 공시를 직접 읽어 보려 했지만 쉽지 않았습니다.
공시는 길고 표가 복잡한 데다 '영업(잠정)실적', '기재정정' 같은 용어가 많습니다. 그래서 공시가 올라와도 무슨 내용인지 바로 알기 어려웠습니다.
같은 매출액이라도 회사마다 단위(백만원, 억원, 조원)가 달라서 숫자를 그대로 비교하기도 힘들었습니다.

stock-insight는 실적 공시의 숫자를 코드로 정리하고, 그 숫자를 바탕으로 3~4문장 요약을 만듭니다.
공시 원문을 열지 않아도 어떤 내용인지 파악할 수 있게 하는 것이 목표입니다.

## 설계 원칙: 숫자는 코드가, 해석은 LLM이

LLM은 문장은 자연스럽게 쓰지만, 숫자를 바꾸거나 직접 계산하다가 틀린 값을 그럴듯하게 쓸 수 있습니다.
요약에서 숫자가 틀리면 서비스의 의미가 없다고 판단해 역할을 나눴습니다.

1. 숫자 정리: 공시 원문 표를 코드로 파싱하고, 단위를 억원으로 통일해 DB에 저장
2. 요약: LLM에는 저장된 숫자만 전달하고, 단위 변환이나 계산은 하지 않도록 지시
3. 검증: 요약에 나온 숫자를 입력 숫자와 비교해, 입력에 없는 숫자가 하나라도 있으면 저장하지 않음

검증에서는 숫자를 문자열로 검색하지 않고 집합으로 비교했습니다.
문자열 검색은 `1,952`처럼 더 긴 숫자 안에 일부로 들어 있는 경우까지 통과시키기 때문입니다.

## 처리 흐름

```
OpenDART API
   ↓ load_corps         상장사 목록 저장
   ↓ load_disclosures   공시 목록 저장, 제목으로 유형 분류
   ↓ load_numbers       실적 공시 표 파싱, 단위 억원 통일
   ↓ load_summaries     LLM 요약 → 숫자 검증 통과한 것만 저장
PostgreSQL
   ↓
FastAPI              공시 목록 / 공시 상세 조회
```

공시 유형은 실적, 회사계획, 주주환원, 기타 네 가지로 나눴습니다.

## 결과

| 항목 | 내용 |
|---|---|
| 수집 | 상장사 4,021곳, 공시 95건 (삼성전자·SK하이닉스, 2026.08.25 ~ 11.25) |
| 파싱 | 실적 숫자 200줄, 단위 3종(백만원·억원·조원)을 억원으로 통일 |
| 요약 검증 | 프롬프트 v1 → v2 수정 후 첫 실행 통과 3/4 → 4/4 |
| 반복 평가 | 함정 공시 4건 × 3회 = 12회, 숫자 검증과 채점 기준 7개 모두 통과 |
| 테스트 | pytest 43개 (파싱, 분류, 요약 검증, API, 채점) |

반복 평가에 쓴 공시는 억원 기본, 조원 정정 공시, 백만원 단위, 음수 증감률이 있는 공시입니다.
평가 세트가 4건으로 작다는 한계가 있어 공시 종류를 늘려 평가를 확장할 계획입니다.

## API

| Method | URL | 설명 |
|---|---|---|
| GET | `/stocks/{stock_code}/disclosures` | 종목별 공시 목록 (`type`, `start`, `end`로 필터) |
| GET | `/disclosures/{rcept_no}` | 공시 상세 (파싱한 숫자, 요약, 근거) |

없는 종목이나 공시는 404, 날짜 형식이 잘못되면 422를 반환합니다.

## 트러블슈팅

### 1. 공시마다 다른 금액 단위

- 문제: 처음 본 삼성전자 공시가 억원 단위라서 모든 공시를 억원으로 가정하고 파싱했습니다.
- 원인: 다른 공시를 확인해 보니 SK하이닉스는 백만원, 삼성전자 정정 공시는 조원이었습니다. 그대로 두면 최대 1만 배 차이 나는 숫자가 오류 없이 저장됩니다.
- 해결: 표의 '단위 : ○○' 칸을 읽어 억원 환산 배수를 곱하도록 바꿨습니다. 등록되지 않은 단위가 나오면 그냥 넘어가지 않고 에러를 내도록 했습니다.
- 결과: 단위 3종을 억원으로 통일했고, 조원 변환 케이스를 테스트로 고정했습니다.

### 2. 너무 넓게 잡힌 분류 규칙

- 문제: 제목에 '배당', '자기주식'이 들어가면 주주환원으로 분류했더니 주주환원이 8건이 나왔습니다.
- 원인: 한 건씩 확인해 보니 5건이 잘못 분류돼 있었습니다. '현금ㆍ현물배당을위한주주명부폐쇄(기준일)결정'은 배당 절차를 알리는 공시였고, '자기주식처분결정'은 오히려 주주환원과 반대 방향의 공시였습니다.
- 해결: 단어가 아니라 공시의 목적을 기준으로 '배당결정', '자기주식취득결정', '자기주식소각결정'만 주주환원으로 분류했습니다.
- 결과: 주주환원 8건 → 3건. 잘못 분류됐던 5건은 회귀 테스트로 남겨 같은 실수가 반복되지 않게 했습니다.

### 3. 맞는 요약을 틀렸다고 판단한 검증

- 문제: SK하이닉스 요약이 숫자 검증에서 떨어져 첫 실행 통과가 4건 중 3건이었습니다.
- 원인: 입력 증감률은 `-58.7`이었고 LLM은 '58.7% 감소'라고 바르게 썼습니다. 그런데 검증이 부호까지 비교해 `58.7`을 입력에 없는 숫자로 판단했습니다.
- 해결: 숫자 검증에서는 부호를 빼고 비교하고, 증가·감소 방향은 별도 채점 기준(`direction_correct`)에서 확인하도록 나눴습니다. 프롬프트 버전을 v2로 올려 결과를 버전별로 따로 저장했습니다.
- 결과: 첫 실행 통과 3/4 → 4/4, 이후 12회 반복 평가에서 모두 통과했습니다.

| 구분 | 기술 |

## 프로젝트 구조

```
stock-insight/
├── app/
│   ├── api/           # API 라우터
│   ├── services/      # 조회 로직 (SQL)
│   ├── llm/           # 요약, 숫자 검증, 채점 기준
│   ├── db.py
│   └── main.py
├── scripts/           # 수집·적재·평가 스크립트
├── sql/schema.sql     # 테이블 정의
├── tests/             # pytest
└── docs/eval/         # 프롬프트 버전별 평가 결과
```

## 실행 방법

```bash
# 1. 패키지 설치
pip install -r requirements.txt

# 2. .env 작성 (.env.example 참고)

# 3. DB 실행 및 테이블 생성
docker run -d --name stock-insight-db -e POSTGRES_PASSWORD=<비밀번호> -e POSTGRES_DB=stock_insight -p 5432:5432 postgres:16
docker exec -i stock-insight-db psql -U postgres -d stock_insight < sql/schema.sql

# 4. 데이터 적재 (순서대로 실행)
python -m scripts.load_corps
python -m scripts.load_disclosures
python -m scripts.load_numbers
python -m scripts.load_summaries

# 5. 서버 실행 후 http://127.0.0.1:8000/docs 접속
uvicorn app.main:app --reload

# 테스트, 요약 평가
pytest
python -m scripts.evaluate_summaries
```
